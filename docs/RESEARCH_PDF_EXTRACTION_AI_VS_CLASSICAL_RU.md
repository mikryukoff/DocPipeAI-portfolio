# Извлечение текста и таблиц из PDF: сравнение классических библиотек и конвейеров на базе ИИ

**Аннотация.** В работе сопоставлены два семейства подходов к извлечению структурированных данных из PDF: (1) библиотечная обработка векторного содержимого и правила без обучаемых моделей в контуре приложения; (2) цепочки с нейросетевой детекцией регионов, классическим OCR слоя и мультимодельным распознаванием текста по изображению. Описан принцип работы типовых инструментов (`pdfplumber`, OCRmyPDF/Tesseract, YOLO, локальный inference VLM). Обсуждаются воспроизводимость, стоимость владения и риски для полей с жёсткой семантикой. Иллюстративные фрагменты кода обобщают распространённые приёмы интеграции.

**Ключевые слова:** PDF, извлечение таблиц, OCR, нейросети, детекция объектов, vision-language models, сравнительный анализ.

---

## 1. Введение

PDF как формат может хранить текст как **векторные операторы** (шрифты, позиции глифов) и как **растровые изображения** страниц или фрагментов. От этого зависит выбор инструментов:

- при наличии нормального текстового слоя достаточно парсинга структуры PDF и эвристик по координатам;
- при сканах и «плоских» страницах без извлекаемого текста нужен OCR и часто **локализация** таблиц и блоков на растре.

Ниже оба пути рассматриваются как **альтернативные стратегии** одной инженерной задачи: получить из документа машиночитаемые строки, ячейки и далее — объекты предметной области (справочники, спецификации, формы).

---

## 2. Подход A: библиотеки без обучаемого ИИ в контуре приложения

### 2.1. Идея

Используются детерминированные алгоритмы: чтение потоков PDF, группировка символов в слова и строки по координатам, восстановление таблиц по **линиям и выравниванию** (или по явной разметке), плюс собственный код очистки и парсинга. Обучаемые нейросети разработчик в этот контур сам не встраивает (под капотом движков вроде Tesseract могут быть свои модели — это «чёрный ящик» внешнего инструмента).

### 2.2. Пример: `pdfplumber` и извлечение текста

Библиотека [pdfplumber](https://github.com/jsvine/pdfplumber) строит для каждой страницы объекты «символ / слово / линия» на основе операторов PDF. Вызов `extract_text()` обычно склеивает текст в порядке чтения потока; для таблиц важны координаты и режимы группировки.

**Принцип работы (упрощённо):** движок раскладывает страницу на геометрические примитивы, затем эвристики выделяют строки и столбцы по близости координат *x* и *y*.

```python
import pdfplumber

with pdfplumber.open("document.pdf") as pdf:

```

### 2.3. Таблицы: `extract_tables` и ручная геометрия

`extract_tables()` ищет на странице **линии** (явные границы ячеек) и/или выравнивает текст по «виртуальной сетке» с параметрами вроде `snap_x_tolerance`, `snap_y_tolerance`: близкие по горизонтали/вертикали координаты объединяются в один столбец или строку.

На практике для шаблонных документов часто задают **обрезку** (`crop` / `within_bbox`) страницы до прямоугольника в координатах PDF, чтобы исключить шум и оставить одну таблицу:

```python
with pdfplumber.open("document.pdf") as pdf:
    page = pdf.pages[0]
    # x0, top, x1, bottom — в точках PDF (72 dpi по умолчанию)
    crop = page.within_bbox((50, 100, 400, 500))
    tables = crop.extract_tables(
        table_settings={"snap_x_tolerance": 1, "snap_y_tolerance": 1}
    )
```

После извлечения обычно нужна **постобработка**: обрезка пробелов, объединение разорванных ячеек, приведение `None` к пустым строкам.

### 2.4. OCRmyPDF и Tesseract как подготовка текстового слоя

[OCRmyPDF](https://ocrmypdf.readthedocs.io/) оборачивает **Tesseract**: растрирует страницы (при необходимости), выполняет OCR, встраивает распознанный текст в **скрытый текстовый слой** PDF, сохраняя визуальный вид. Это не замена табличного парсера, но после такого шага `extract_text()` снова может что-то вернуть даже для сканов.

Типичный вызов (иллюстрация параметров из практики):

```python
import ocrmypdf

ocrmypdf.ocr(
    input_file="scan.pdf",
    output_file="searchable.pdf",
    language="rus+eng",
    deskew=True,
    force_ocr=True,
)
```

`deskew` выравнивает наклон; `force_ocr` заставляет перераспознать страницу даже при наличии старого текстового слоя (применять осторожно: может ухудшить уже корректный векторный текст, если включать вслепую).

## 3. Подход B: конвейеры с ИИ и нейросетевыми компонентами

### 3.1. Детекция таблиц и блоков (YOLO)

**Задача:** на изображении страницы найти прямоугольники класса «таблица» (или другие классы). Семейство **YOLO** (например, YOLOv8 в [Ultralytics](https://docs.ultralytics.com/)) предсказывает bounding box и класс за один проход сети; инференс относительно быстрый.

**Принцип работы (упрощённо):** страница PDF конвертируется в растр (`pdf2image` + Poppler), изображение подаётся в модель; на выходе — список координат `[x1, y1, x2, y2]` в пикселях. Дальше по этим координатам вырезают фрагменты и либо отдают в OCR/VLM, либо масштабируют обратно в систему координат PDF.

![Рисунок 3. Детекция таблиц на растре страницы (пример выхода YOLO)](_figures/03_yolo_table_boxes.png)

Иллюстративный каркас (без привязки к конкретному репозиторию весов):

```python
from pdf2image import convert_from_path
from ultralytics import YOLO

model = YOLO("table_detector.pt")  # веса заранее обучены / скачаны
pages = convert_from_path("document.pdf", first_page=1, last_page=1)
img = pages[0]
results = model(img, conf=0.3)
boxes = results[0].boxes.xyxy.tolist()  # список прямоугольников
```

Веса часто берут с **Hugging Face Hub**; качество сильно зависит от сходства ваших документов с обучающими данными.

### 3.2. Распознавание текста с фрагмента изображения (VLM через локальный API)

**Vision-language model** принимает изображение и текстовую инструкцию; на выходе — сгенерированная строка. Такой приём используют как «гибкий OCR»: не настраивать цепочку предобработки, а попросить модель вернуть видимый текст. Минусы: вариативность ответа, возможные галлюцинации, зависимость от промпта и версии модели.

Локальный сервер [Ollama](https://github.com/ollama/ollama) позволяет вызывать модель с полем `images` в запросе. Упрощённый асинхронный паттерн:

```python
import asyncio
from ollama import AsyncClient

async def image_to_plain_text(image_bytes: bytes, host: str = "http://localhost:11434") -> str:
    client = AsyncClient(host=host)
    response = await client.generate(
        model="glm-ocr",  # условное имя; замените на свою vision-модель
        prompt=(
            "Extract the text from this image and return it strictly as plain text. "
            "Do not include any explanations or markdown code blocks, just the text."
        ),
        images=[image_bytes],
        stream=False,
        options={"temperature": 0.0, "top_p": 0.1},
    )
    return (response.get("response") or "").strip()
```

Низкая **temperature** и **top_p** снижают разброс ответов; всё равно нужна пост-валидация (регулярные выражения, допустимые диапазоны чисел, справочники).

### 3.3. End-to-end Document AI (перспектива)

В исследованиях и продуктах развиваются **layout-aware трансформеры** и модели **восстановления структуры таблицы** (иерархия строк/столбцов, объединённые ячейки) без явной ручной сетки. Это отдельный класс решений: выше требования к данным для дообучения и к инфраструктуре, ниже — ручная кустарная геометрия на каждый шаблон. В типичном «гибридном» продукте такой блок может сосуществовать с pdfplumber, а не полностью его заменять.

## 4. Сводная схема двух стратегий

Здесь намеренно **нет блоков Mermaid**: в разных редакторах и на GitHub версии движка различаются, из‑за чего диаграммы то отображаются, то показываются как ошибка разметки. Ниже — **текстовая схема**, которая везде выглядит одинаково; при подготовке PDF/Word можно оформить её как рисунок вручную или вставить экспорт из draw.io.

Связь «скан → OCRmyPDF → затем pdfplumber» (**гибрид**) показана отдельным блоком ниже: после появления текстового слоя дальше идут те же шаги, что в подходе A.

**Подход A — библиотеки и правила**

```text
  +----------------+     +-------------+     +------------+     +------------------+
  | PDF text layer | --> | pdfplumber  | --> | Rules crop | --> | Structured data |
  +----------------+     +-------------+     +------------+     +------------------+
```

**Подход B — растр и ML**

```text
  +-------------+     +-------------+     +---------------+     +--------------+     +------------------+
  | PDF / scan  | --> | Raster page | --> | YOLO detector | --> | VLM line OCR | --> | Text coordinates |
  +-------------+     +-------------+     +---------------+     +--------------+     +------------------+
```

**Гибрид (дополнительно к цепочкам выше):**

```text
  +-------------+     +----------------------+     +----------------+
  | PDF / scan  | --> | OCRmyPDF + Tesseract | --> | PDF text layer |
  +-------------+     +----------------------+     +----------------+
                              |
                              v
         pdfplumber --> Rules crop --> Structured data   (как в подходе A)
```

| Узел (как на схеме) | Смысл (RU) |
|---------------------|------------|
| PDF text layer | PDF с извлекаемым текстовым слоем |
| pdfplumber | Извлечение текста/таблиц библиотекой pdfplumber |
| Rules crop | Правила и обрезка по bbox |
| Structured data | Структурированные данные |
| PDF / scan | PDF или скан |
| Raster page | Растр страницы |
| YOLO detector | Детектор областей (YOLO) |
| VLM line OCR | Мультимодель или построчный OCR по фрагменту |
| Text coordinates | Текст и координаты |

После гибридного OCR цепочка продолжается узлами подхода A: `pdfplumber` → правила → структурированные данные.

## 5. Сравнительный анализ

| Критерий | Подход A (pdfplumber + правила, при необходимости OCRmyPDF) | Подход B (YOLO + VLM / тяжёлый OCR) |
|----------|-----------------------------------------------|--------------------------------------|
| Воспроизводимость | Высокая при стабильных шаблонах | Зависит от весов, версии модели, промпта |
| Сканы без текстового слоя | Нужен OCR-слой; таблицы по линиям всё равно сложны | Естественная область применения |
| Инфраструктура | Часто достаточно CPU | GPU для инференса; память под модели |
| Объяснимость | Понятные координаты и правила | «Чёрный ящик»; нужны тесты и метрики |
| Сопровождение | Рост числа `crop` и исключений | Мониторинг дрейфа, переобучение, A/B |

**Ограничения VLM:** для идентификаторов, кодов по стандарту и числовых полей с юридическим значением ответ модели нельзя принимать без **проверки** (схема JSON, допустимые значения, сверка с вторым источником).

**Сильная сторона классики:** один и тот же PDF даёт тот же извлечённый текст при неизменной версии библиотеки и явных параметрах — удобно для регламентированных процессов и аудита.

## 6. Заключение

Классический путь на базе **pdfplumber** и детерминированного постпроцессинга остаётся основой там, где PDF содержит корректный текстовый слой и макет поддаётся эвристикам. **OCRmyPDF** логично стоит на стыке: это не «ИИ-таблицы», но снимает проблему отсутствия текста для последующего парсинга. **ИИ-компоненты** (детекция регионов, VLM) расширяют покрытие на нестандартные и сканированные документы, но требуют дисциплины валидации и инфраструктуры.

Практичная стратегия — **гибрид**: по эвристикам выбирать ветку; хранить конфигурации областей и версии моделей; для критичных полей не полагаться на генеративный вывод без проверки.
